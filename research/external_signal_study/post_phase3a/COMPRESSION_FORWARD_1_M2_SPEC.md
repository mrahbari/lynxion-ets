## Exact M2 rule

| Element | Frozen definition |
| --- | --- |
| Instrument/source | Public **Binance USDⓈ-M BTCUSDT perpetual** OHLCV, the same declared proxy venue/instrument family as Phase 3A. Use the exchange's 15-minute kline open timestamps and OHLCV; no spot, BingX, index, or cross-venue substitution. Preserve endpoint/source manifest, acquisition time, exchange timezone, raw file hash, and gap audit. |
| Base and regime timeframe | Complete **UTC 1-day** BTC bars, each assembled from exactly 96 contiguous Binance perpetual 15-minute bars with opens at `00:00, 00:15, …, 23:45 UTC`. Daily open is the first bar's open; daily close is the last bar's close. Daily bar availability is the last component's exchange close time (`23:59:59 UTC` under the Phase 3A `open+899s` convention). An incomplete current UTC day is never used. |
| Volatility estimator | For each fully completed daily bar `d`, let `r_d = ln(close_d / open_d)`. For an endpoint day `e`, `V_e` is the **sample standard deviation** (`ddof=1`, no annualization) of the 30 consecutive daily returns `r_(e-29)…r_e`. Require positive finite OHLC prices. No absolute-return, high–low, ATR, EWMA, or direction adjustment. Daily open/close gives precisely 30 returns from the frozen 30 completed daily candles. |
| Current lookback | At each case or control timestamp `T`, let `e` be the most recent UTC day whose full daily bar closed at or before `T`. Compute current `V_e` from days `e-29…e`, all completed before T. |
| Historical reference and terciles | Compute exactly 90 earlier, rolling 30-day estimates `V_(e-30), V_(e-31), …, V_(e-119)`. Thus every reference window ends **before** the first day of the current 30-day window. Sort these 90 finite values ascending; lower boundary `Q1` is sorted item 30 (index 29), upper boundary `Q2` is item 60 (index 59): the fixed nearest-rank 1/3 and 2/3 empirical cutoffs. The baseline is not refit using F4, signal labels, or later dates. If `Q1 >= Q2`, regime is missing (degenerate baseline). |
| Minimum history | All UTC days `e-148…e` must have exactly 96 valid, contiguous 15-minute bars: **149 complete daily bars**. This covers the current 30-day estimator and all 90 disjoint-prior reference endpoints and their rolling windows. No interpolation, forward fill, alternate source, shorter lookback, or partial-window estimate. |
| UTC alignment | At every `T`, use that record's own last completed UTC day `e`, not the case's day for its controls. An event on UTC day `D` uses at most `D-1`. Availability time of every 15-minute component and derived daily bar must be `<= T`; record `T`, `e`, source hash, and maximum input close in the audit. UTC daylight-saving adjustments are never applied. |
| Regime assignment | `LOW` when `V_e <= Q1`; `MID` when `Q1 < V_e <= Q2`; `HIGH` when `V_e > Q2`. Ties follow those inequalities exactly. A regime is assigned using BTC market data only, without case/control F4 values or post-T information. |
| Missing data | Any absent/duplicate/noncontiguous 15-minute component, nonpositive/nonfinite price, nonfinite volatility, degenerate reference cutoffs, unverified source hash, or delayed/uncertain timestamp makes that *record's* M2 regime `MISSING`. Do not substitute a neighboring day or drop a bar. Log reason and retain the record in an attrition audit. |
| Case/control treatment | First form the frozen M1 Family-A controls **unchanged**: same symbol, side/timeframe, ISO week and four-hour UTC block, ±6-hour all-sibling-signal exclusion, complete pre-T coverage, up to three distinct-date controls by the original SHA-256 ordering. Only then assign a BTC regime to each case and each *already selected* M1 control at its own T. For M2, retain only M1 controls with the **same** nonmissing regime as the case; require at least two retained controls. Do not redraw, rerank, replace, or relax M1 controls to improve M2 retention. M1 primary results remain untouched. |
| M2 estimand and sign | For each matched M2 case, compute the *same frozen F4* case value minus the arithmetic mean of its 2–3 retained controls. The M2 sensitivity effect is the arithmetic mean of those per-case differences, with each case weighted once. **Sign retention** means this mean is strictly positive, the same sign as the predeclared prospective F4 lead; zero, negative, or missing fails sign retention. Report a day-cluster uncertainty interval descriptively; do not use an M2-only p-value or a new magnitude cutoff to rescue the lead. |
| Interpretable breadth | At least **40** M2-matched cases over **20 distinct case UTC days**, **10 symbols**, and **10 LONG plus 10 SHORT** cases, preserving the original primary breadth floor. Additionally, each of LOW/MID/HIGH must contribute at least **10 matched cases on five distinct UTC days**; otherwise the broad three-regime sensitivity is `M2_INSUFFICIENT_BREADTH`, not a passed sign check. Report nominal count, M1-to-M2 attrition, days, symbols, sides, and each regime separately. These are minimum interpretability gates, not a replacement for the prospective study's >=80% power requirement. |

**Methodological rationale:** A 30-completed-day sample standard deviation measures broad BTC volatility without using current-day or future information. A 90-endpoint, prior, nonoverlapping reference period provides a local historical regime distribution while keeping the current 30-day measurement out of its own cutoffs. The nearest-rank terciles, deterministic tie rule, strict gaps, and M1-first filtering prevent result-dependent regime assignment or control fishing. More history and regime breadth may make M2 data-hungry; that is a measurement cost, not grounds to change this rule after seeing contrasts.

**M3: `NOT_IDENTIFIABLE`.** Same ISO week + same weekday + same UTC four-hour block puts every proposed control within four hours of its case, conflicting with the frozen ±6-hour same-symbol signal exclusion. This document does not repair or weaken M3. It is reported as unavailable sensitivity, not an automatic veto or a substitute for M2.
