## Producer → interpreter → Fusion

1. `HistoricalCandleWatcherAdapter._determine_observation_type` labels pattern/trend combinations `candle_reversal_bullish_emerging`, `candle_reversal_bearish_emerging`, `candle_confirmation_*`, etc. The labels describe analytical pattern context; `MarketObservation` is explicitly raw watcher output, not a trading decision. Its `observation_value` is `0.7 * trend_direction + 0.3 * pattern_strength`, not a declared signed order side. Pattern strength can contribute positively even to a bearish label. The current implementation contains two methods named `_determine_observation_type`; the later definition wins. The reversal labels came from historical watcher development (`git blame`: `666e8233`/`1f17a804`), not from an accompanying Engine mapping.
2. `EngineService.process_observation` is the active `MarketObservation` → `InterpretedSignal` interpreter. Its `_determine_signal_type` handles market pulse, trend, momentum, volatility, liquidity, anomaly and single-candle families. It has no `candle_reversal`/`candle_confirmation` branch; unknown types return `SignalType.NEUTRAL`. The Engine's neutral default predates the current reversal labels (`c69492a` versus `666e8233`/`1f17a804`). No source, test or design artifact inspected specifies one unique intended BUY/SELL mapping for these types. A positive numeric `direction` in an `InterpretedSignal` does not override its NEUTRAL `signal_type`.
3. Live `MonitoringAnalysisService._analyze_symbol` attaches its registry key as `observation.metadata['watcher_name']` before publishing. The key is `historical_candle` in `WatcherInitializationService`; hierarchical Fusion classifies it as a DIRECTION watcher. The original Replay driver omitted this metadata. Engine then could not infer a source watcher from `candle_reversal_*`, and `FusionService` used its enhanced single-input fallback. This is a **proven Replay wiring difference**, reproduced by a red test and corrected in `fbb5a34` by adding only the existing registry key before publication. No Fusion/Engine rule changed.
4. With correct watcher identity, `FusionService.fuse_signals` enters hierarchical Fusion. The current shared `SignalProcessor._process_interpreted_signal` invokes `fuse_signals([signal])`: exactly one interpreted signal per event, in Live and Replay. `ConflictResolutionRules._resolve_direction_conflicts` requires at least **two aligned direction observations**; one returns `insufficient_aligned_direction_signals`. This is an explicit existing rule, not a replay threshold. The defined one-watcher/one-event pre-intent subset therefore cannot obtain hierarchical BUY/SELL under current composition, even if the textual reversal label is directionally suggestive. Altering batching, lowering the two-signal requirement or mapping Engine types would be a new economic/decision semantic choice, not mechanical replay repair.

## Live comparison and limits

The inspected auto-detection Live composition constructs `MarketOpportunityWatcher` → `MonitoringAnalysisService` with the same router/Engine/Fusion classes. However, its market-data formatter passes flat `open/high/low/close/...` fields to each watcher, while `HistoricalCandleWatcherAdapter.update_data` appends only `data['candle']`. A focused local test confirms flat input leaves its candle buffer empty, whereas nested candle input fills it. This feed mismatch was independently noted in `docs/reports/unused_data_inventory.md`. Thus the current historical watcher appears starved in this **inspected Live monitoring path**; no running-process claim and no claim about every possible caller is made. Replay deliberately supplies validated completed bars in nested form for the separately frozen candle-only subset. That subset is not full Live watcher parity.

Historical source inspection found no alternate production interpreter that converts `candle_reversal_*` to a declared order side. Other EnginePort adapter families documented in `docs/reports/E3.T7-engine-discovery.md` are not the active `EngineService` path. Replacing this watcher or bypassing Engine would change the frozen study boundary. Fusion's multi-watcher design describes corroboration, but the current event processor supplies singleton lists; the repository does not define a unique timing/batching contract for changing that Live behavior.
