## 2. Root Cause Analysis & Code Locations

### Issue 1 — Burst of Orders Immediately After Startup

#### Observed Behavior
Within the first 3–4 minutes after startup, the system opened approximately 6 orders, all generated by the `MTFTrend` strategy, followed by a long period of inactivity.

#### Root Cause
1. **Historical Buffer Replay**: On startup, `MonitoringAnalysisService._monitoring_loop` retrieves 100 historical candles using `market_data_repo.get_historical_data` and populates the watchers' buffers using `_initialize_watcher_histories_with_historical_data`.
2. **Lack of Setup Freshness Verification**: When `MTFTrendStrategyAdapter.generate_signal` executes, it calls `self.setup_engine.scan_for_setups(symbol, prices, highs, lows, val, vah, poc)` to scan the entire 100-candle buffer. The adapter takes the *first* setup matching `NGTREND_FOLLOW` from the returned list without validating that the setup actually occurred on the *latest* (index `-1`) bar.
3. **Signal Storm**: Because old setups still present in the historical buffer are treated as active live signals, the system publishes them to the event system immediately upon start, resulting in a burst of execution intents.
4. **Natural Stoppage**: The burst stopped after 3–4 minutes because the exchange order limits or the system's broker duplicate prevention mechanism (`_check_broker_active_orders_for_duplicate` and `PendingOrdersTracker`) locked subsequent attempts after initial fills.

#### Code Locations
* [mtf_trend_strategy_adapter.py](file:///Users/mojtaba.rahbari/Sites/python/lynxion-ets/infrastructure/strategies/adapters/mtf_trend_strategy_adapter.py#L33-L79) — `generate_signal` does not check if the setup is located at the tail of the price list.
* [monitoring_analysis_service.py](file:///Users/mojtaba.rahbari/Sites/python/lynxion-ets/infrastructure/watchers/monitoring_analysis_service.py#L290-L305) — `_initialize_watcher_histories_with_historical_data` feeds the buffer on startup.

#### Classification
* **Defect (Bug)** in strategy adapter setup-matching logic.

#### Minimal Remediation Plan
Update `MTFTrendStrategyAdapter.generate_signal` to assert that the setup's trigger bar matches the latest bar index or timestamp before returning a signal.

#### Priority
* **High**

### Issue 2 — HEARTBEAT GUARD VETO Spam

#### Observed Log
`❌ HEARTBEAT GUARD VETO: Market data heartbeat is stale by 3314.1s (>90s)`

#### Root Cause
1. **Incorrect Update Trigger**: The `_last_market_data_times` dictionary is used by the `SignalProcessor` in the event system to check if market data ingestion is live.
2. **Event Dependencies**: Currently, `_last_market_data_times` is only updated when a `MARKET_OBSERVATION` event is processed. However, a `MARKET_OBSERVATION` event is only emitted when a watcher successfully detects a technical pattern or opportunity.
3. **False Positives**: If a symbol is quiet and no patterns are detected, no observation is emitted. This causes the heartbeat to appear stale by thousands of seconds, even though the watcher is continuously and successfully fetching new market data every 30 seconds.

#### Code Locations
* [event_system.py](file:///Users/mojtaba.rahbari/Sites/python/lynxion-ets/infrastructure/messaging/event_system.py#L176-L179) — `_last_market_data_times` updated only inside `_process_observation`.
* [event_system.py](file:///Users/mojtaba.rahbari/Sites/python/lynxion-ets/infrastructure/messaging/event_system.py#L507-L526) — Heartbeat guard checks the timestamp.
* [monitoring_analysis_service.py](file:///Users/mojtaba.rahbari/Sites/python/lynxion-ets/infrastructure/watchers/monitoring_analysis_service.py#L170-L250) — Market data is fetched but heartbeat is not updated here.

#### Classification
* **Design Limitation / Bug** in heartbeat state tracking.

#### Minimal Remediation Plan
Directly update the global `signal_processor._last_market_data_times` entry inside `MonitoringAnalysisService._update_watchers_with_market_data` immediately after a successful market data fetch.

#### Priority
* **Medium**

### Issue 3 — Unexpected Large Position ($17,035)

#### Observed Behavior
Most orders were below $40, but one SOL order was sized at approximately $17,035.

#### Root Cause
1. **Dynamic Sizing Behavior**: The sizing of the SOL order was calculated using the NGDP dynamic sizing algorithm (`calculate_dynamic_size` resolving to `calculate_position_size` with `fixed_position_size_enabled = False`).
2. **Stop Loss Closeness**: Dynamic position sizing evaluates quantity as `risk_amount / risk_per_unit` (where `risk_per_unit = abs(entry - stop_loss)`). When a strategy places a very close stop loss (e.g. 1%), the risk per unit is small, causing the quantity (and total exposure) to swell.
3. **Limits Complied**: While the exposure was large relative to fixed-size orders ($4), it did not breach the global max position exposure limit ($50,000), so the Risk Engine correctly approved it.
4. **Lack of Per-Order Cap**: The system currently lacks an absolute per-order notional value cap to restrict large orders regardless of close stop losses.

#### Code Locations
* [enterprise_risk_manager.py](file:///Users/mojtaba.rahbari/Sites/python/lynxion-ets/application/risk_management/enterprise_risk_manager.py#L182-L197) — Sizing formula scales inversely with stop loss distance.

#### Classification
* **Expected Sizing Behavior** (NGDP dynamic sizing working as intended), but represents a configuration/design requirement gap.

#### Minimal Remediation Plan
Introduce a `MAX_ORDER_NOTIONAL_USD` configuration option. In `RiskEnforcement.enforce`, if this option is configured and the order notional value exceeds it, cap the `order.quantity` to stay within the limit before broker submission.

#### Priority
* **Medium**

### Issue 4 — Strategy Diversity

#### Observed Behavior
Only the `MTFTrend` strategy generated trades during the runs.

#### Root Cause
1. **Technical Setups Not Triggered**: All strategies are enabled and evaluated on each loop, but they return `None` because the market data buffer does not satisfy their specific pattern setups (e.g., `NGMR_REVERSION` for VWAP/Mean Reversion).
2. **Strict Strategy Admission**: This is expected behavior; strategies should only trigger when their exact entry setups are matched in the price buffer.

| --- | :---: | :---: | :---: | :---: | :---: | --- |

| **Breakout** | Yes | Yes | No | No | No | Breakout setup conditions not met in price buffer |

#### Classification
* **Expected Behavior** (strategies functioning defensively).

#### Minimal Remediation Plan
No code modification is required.

### Issue 5 — Signal Contradiction

#### Observed Log
`⚠️ Signal contradiction: Bias=SELL vs Order=BUY`

#### Root Cause
1. **Multi-Horizon Divergence**: The `FusionService` aggregates global/macro sentiment to compute market bias (e.g., `SELL` on hourly timeframe).
2. **Local Triggers**: Individual strategies evaluate local setups (e.g., a short-term oversold bounce on the 1-minute chart).
3. **Horizon Mismatch**: A local strategy may trigger a `BUY` order when the macro bias is `SELL`.
4. **Veto Policy**: The system logs this divergence as a warning but does not block it by default, which is correct because blocking it would disable mean-reversion and scalping strategies.

#### Code Locations
* [event_system.py](file:///Users/mojtaba.rahbari/Sites/python/lynxion-ets/infrastructure/messaging/event_system.py#L409-L418) — Comparison of dominant bias with order side.

#### Classification
* **Expected Behavior** (cross-timeframe divergence warning).

#### Minimal Remediation Plan
Retain the warning log for visibility; do not introduce execution blocks unless a trend-alignment filter is explicitly requested.

#### Priority
* **Low**
