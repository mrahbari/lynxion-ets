## 0. Bottom line

pandas **is** present in the domain layer today, in **exactly two files** (both named in
the task). The contamination is small and well-contained:

- **`domain/engines/engine_interface.py`** — `EngineInterface` Protocol. **100% dead

(`backtest_ports.py`, `data_ports.py`) were already made pandas-free in E3 via the
`Any` + docstring pattern — that is the established house precedent for this exact
problem.

## 5. Classification

### ✅ Safe mechanical removal (no behavior change, no boundary work)
- **`domain/engines/engine_interface.py`** — dead; replace `pd.DataFrame` → `Any` and drop
  the import (or delete the file outright, see §7 decision D2).
- **`optimization_ports.py` — all six pandas signatures** — replace `pd.DataFrame`/`pd.Series`
  → `Any` and drop the import. Implementers retain concrete pandas types; the single live
  caller path (`load_historical_data`) is duck-typed; metric methods have no live caller.
  This mirrors the **already-accepted E3 precedent** (`backtest_ports`, `data_ports`).

### ⚠️ Adapter boundary required (only if the literal constraint is enforced)
- The task says "move pandas-typed signatures to **DTOs**; domain speaks **entities/VOs**."
  Satisfying that *literally* for `load_historical_data -> pd.DataFrame` means introducing a
  domain representation of OHLCV tabular data (e.g. `Sequence[MarketData]` or a new
  `MarketDataFrame` VO) **plus** an adapter that converts DataFrame↔VO at the infra boundary,
  and updating the 5 live call sites + downstream backtest/hyperopt consumers (which expect a
  DataFrame). This is a cross-cutting change well beyond the two named files.

### 🧭 Architecture decision required
- **D1 — `Any` vs. true VO/DTO.** Does the established `Any` + docstring pattern (E3) satisfy
  E4.T3's "domain speaks entities/VOs", or is a real tabular VO mandated? `Any` = minimal,
  precedent-consistent, low-risk, achieves `grep==0`. True VO = higher fidelity but large blast
  radius across the optimization/backtest data flow.
- **D2 — neutralize vs. delete `engine_interface.py`.** It is dead. Deleting it (and the empty
  `domain/engines/` dir) is cleanest, but file deletion is scope-sensitive here — "engines" are
  a flagged core-architecture element and a prior E8 engine-cleanup was **reverted** by the user.
  Neutralize-in-place (→ `Any`) is the zero-risk E4.T3 move; deletion should be deferred to an
  explicitly-authorized E8 step.

## 7. Migration plan (recommended: `Any` pattern, neutralize-in-place)

1. `domain/ports/optimization_ports.py`: drop `import pandas as pd`; change the 6 annotations
   `pd.DataFrame`/`pd.Series` → `Any` (already imported); add a one-line docstring note per
   the `backtest_ports.py` precedent ("typed `Any`; concrete pandas types live in the infra
   adapter"). Implementers in `infrastructure/optimization/__init__.py` unchanged.
2. `domain/engines/engine_interface.py`: drop `import pandas as pd`; change `pd.DataFrame` →
   `Any`. (Defer outright deletion to E8 per D2.)
3. Verify `grep -rn "import pandas" domain/` → 0; `py_compile` domain; import `domain.ports.optimization_ports`
   + `domain.engines.engine_interface`.
4. (Deferred / E6.T4) Stand up mypy-strict config and run on `domain/` to close the second
   acceptance clause.

**Alternative (literal-constraint) plan** — only if D1 rules for true VOs: define
`domain/value_objects` tabular type (or `Sequence[MarketData]`), add a
DataFrame↔VO adapter in `infrastructure/optimization`, migrate the 5 `load_historical_data`
call sites + downstream. Larger, separate task; not recommended for E4.T3's stated 2-file scope.
