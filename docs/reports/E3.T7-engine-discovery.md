# E3.T7 — Engine System Discovery & Consolidation Preparation

**Status:** Read-only discovery. **No code was modified.**
**Scope:** Full non-invasive analysis of the signal-engine ecosystem prior to any
`EnginePort` consolidation.

> Guiding principle (per task): *"Do not unify anything until you fully understand
> every signal generator."* This document is the prerequisite understanding.

---

## 0. EXECUTIVE SUMMARY (read this first)

The single most important finding overrides everything else in the plan:

> **There is no live, working `EnginePort` engine in the system today.**
> Every discrete signal-processing engine (Trend, Volatility, Correlation, Orderflow,
> Liquidity, ML Weight, ATR, Regime) is **dead code** — it is never instantiated by the
> active container, and most of it **cannot even run** against the current domain entities.

Three independent facts establish this:

1. **Not wired.** The live DI container (`bootstrap/container.py`, entered via
   `bootstrap/lifecycle.py:lifespan()` and used by both CLI entrypoints) registers exactly
   **one** engine-named component: `engine_service` →
   `infrastructure/engines/engine_service.py:EngineService`. None of the 8 engines, none of
   the aggregation adapters (`EngineCollectionAdapter`, `EngineManagementService`,
   `WorkflowOrchestrator`), and none of `dynamic_engine_manager.py` are ever constructed in
   production wiring.

2. **`EngineService` is not an `EnginePort`.** It implements `process_observation()`
   (the `ObservationProcessorPort` contract, `engine_ports.py:119`), converting a
   `MarketObservation` → `InterpretedSignal`. It has no `process_signal`,
   `should_process_signal`, or `get_engine_name`. The thing the pipeline actually calls
   "the engine" is a *watcher-observation interpreter*, not an `EnginePort`.

3. **The `EnginePort` adapters are broken against current entities.** All `EnginePort`
   engine adapters construct `Signal(..., strategy_name=..., source_engine=...)`, but the
   canonical `domain/entities/signal.py:Signal` has **no `strategy_name` and no
   `source_engine` field** (confirmed: those identifiers do not appear in `signal.py`).
   Any attempt to run them raises `TypeError`. They were written against an older `Signal`
   shape that no longer exists (entities were split/renamed in E4.T1 shims).

**Consequence for T7 implementation:** "Consolidate the engines behind `EnginePort`" is, as
literally stated, a consolidation of code that is already dead and partly non-compilable at
runtime. The honest first decision is **not** "how do we unify these 8 engines" but **"do we
resurrect them at all, or do we formally retire them and define `EnginePort` around the one
engine that is actually live (the observation processor)?"** See §6 and §7.

## 2. SIGNAL FLOW GRAPH

### 2.1 The LIVE pipeline (what actually runs)
```
Watcher(s)
   │  emit MarketObservation (domain/entities/signal.py:MarketObservation)
   ▼
shared/event_system.py:_process_observation(event, engine_service)   [event-driven]
   │  engine_service.process_observation(observation)            (engine_service.py:18)
   ▼
EngineService  ── _determine_signal_type / _calculate_direction / _calculate_strength ──►
   │  returns InterpretedSignal  (NOT a Signal, NOT via EnginePort)
   ▼
Fusion service ──► Strategy ──► Risk ──► Broker/Execution
```
Orchestrators on the live path: `infrastructure/orchestrators/auto_detection_orchestrator.py:45`
and `architecture_orchestrator.py:12` both grab `engine_service` and call
`process_observation`. **No discrete engine is consulted between watcher and fusion.**

### 2.2 The INTENDED (dormant) `EnginePort` pipeline (exists only in dead code)
```
raw Signal
   ▼
EngineCollectionAdapter / EngineManagementService / WorkflowOrchestrator
   │   for engine in engines:
   │       if engine.should_process_signal(s): s = engine.process_signal(s)   [SEQUENTIAL CHAIN]
   ▼
fused Signal
```
- **Branching point:** `should_process_signal()` gate per engine (most return `True`/data-length checks).
- **Topology:** strictly sequential **pipe** (output of engine N feeds engine N+1), *not* a parallel
  score-then-aggregate fan-in. There is **no aggregation/voting** in the chain adapters — each engine
  multiplicatively mutates confidence/score in place. Order therefore changes the result
  (non-commutative; see §5).
- **A parallel score+aggregate model exists separately** in `dynamic_engine_manager.py`
  (`EnsembleEngineFusion.fuse_engine_outputs` → weighted_average / ml_based / confidence_weighted /
  majority). It expects `Dict[engine_name, score]` inputs, i.e. a *different* engine contract than
  the chain. These two mental models (chain vs. ensemble) are mutually incompatible and both dormant.

### 2.3 Hidden coupling / implicit dependencies
- **Cross-engine metadata coupling:** `MLWeightEngine` reads `metadata['volatility_regime']` and
  `metadata['trend_aligned']` (`ml_weight_engine.py:92,103`) that only exist if Volatility/Trend ran
  **earlier in the chain**. → implicit ordering dependency (ML must run after Vol/Trend).
- **`RegimeEngineAdapter` (Family B)** branches on `signal.strategy_name` substring
  (`'trend'`, `'revert'`/`'mean'`, `engine_adapters.py:617-618`) — couples engine behavior to
  strategy *naming convention*.
- **`OrderFlow`/`Liquidity`** require `data['bids']`/`data['asks']` in `update_with_market_data`;
  the live observation feed supplies OHLCV, not order books → these engines would stay in their
  "no data" fallback branch indefinitely even if wired.
- **Two `BaseEngineAdapter` classes** with the same name (`infrastructure/engines/base_engine_adapter.py`
  vs `infrastructure/engines/adapters/engine_adapters.py:63`) — import-path ambiguity hazard.

## 6. ENGINE PORT DESIGN RISK ANALYSIS

**Can all engines fit a single `EnginePort` interface?** Structurally yes (they share the
`process_signal / should_process_signal / update_with_market_data / get_engine_name` shape), **but**:

1. **Type contract is already inconsistent and partly wrong.**
   - Port says `InterpretedSignal`; adapters use `Signal`; the entity `Signal` lacks the
     `strategy_name`/`source_engine` fields the adapters write. Forcing one contract requires first
     **choosing one Signal type and fixing every adapter** — that is behavior-changing, not a rename.
2. **`update_with_market_data` is polymorphic in disguise.** Trend/Vol/Regime/ATR want OHLCV;
   Orderflow/Liquidity want `bids`/`asks`. A single `Dict[str,Any]` "works" only by silently
   no-op'ing engines whose required keys are absent. → a unified port hides capability differences.
3. **`MLWeightEngine` doesn't fit the stateless transform model.** It needs a *feedback* method
   (`record_signal_performance`) that the port doesn't express. Either it's not an `EnginePort` or
   the port must grow a learning/feedback surface (→ argues for a **split**, see below).
4. **Chain vs. ensemble are different ports.** Sequential `process_signal` (mutate-in-place) and
   ensemble `Dict[name,score]→fused` (`dynamic_engine_manager`) cannot both be `EnginePort`. The
   weight-manager/selector/fusion belong behind a **separate `FusionPort`/`EngineEnsemblePort`**, not
   `EnginePort`.
5. **Polymorphism breaks on output identity.** Some engines return a *new* signal type-name
   (`source_engine=self.name`), the chain depends on order; ensemble depends on independent scores.
   A single contract can't be simultaneously order-dependent and order-independent.

**Verdict:** A **single** `EnginePort` is feasible only as a *scoring* contract
(`evaluate(signal/observation, market_context) -> score+metadata`, side-effect free, order-independent).
The current "mutate confidence in a chain" model should **not** be the canonical port — it bakes in
the ordering coupling and the broken entity fields.

**Recommended multi-port split:**
- `EngineScoringPort` — pure `score(context) -> EngineResult`-like (one number + metadata, no mutation).
- `EngineEnsemblePort` / keep `FusionPort` — aggregates `Dict[engine, EngineResult]` → fused signal
  (home for `dynamic_engine_manager`).
- (optional) `EngineFeedbackPort` — `record_outcome(...)` for the ML/online learner only.
- Leave `ObservationProcessorPort` (the live `EngineService`) **as-is**; do not conflate it with
  `EnginePort`.

## 7. MINIMAL SAFE CONSOLIDATION STRATEGY (NO CODE)

Ordering is chosen to maximize safety given that the live system does **not** depend on these engines.

**Phase 0 — Decision gate (RATIFIED → Option A).**
> **DECISION (architecture ownership): Option A — Retire & Redefine.**
> EngineService (`process_observation`) is declared the canonical engine layer. `EnginePort` is to
> be redefined around the live production flow. The 8 legacy engine families are deprecated; physical
> removal is scheduled for E8. Resurrection (Option B) is explicitly rejected: E3 is a consolidation
> epic, not a feature-resurrection epic. Implementation of this decision is a **separate follow-up
> task (E3.T7.1)** — it is out of scope for this read-only discovery (E3.T7).

Original gate framing (now resolved):
- **(A) Retire-and-redefine** (recommended): the 8 engines stay dead; `EnginePort` is redefined as a
  pure scoring contract and the only conformant implementation initially is a thin wrapper around the
  live observation processor. Dead families are deleted in a later E8 cleanup task, not now.
- **(B) Resurrect-then-consolidate**: the 8 engines must become live. This is a *much* larger,
  behavior-introducing effort (fix entity fields, wire into `bootstrap/container.py`, define
  ordering, build the full Watcher→Engine→Fusion chain) and is **out of scope for a "consolidate
  behind a port" task**.

> The task title implies (A)-style consolidation; the codebase reality is that there is nothing live
> to consolidate. **Do not start coding until this gate is answered.** (RULE 1 / RULE 5: don't invent
> architecture beyond the task.)

**Phase 1 — Pin the only live behavior.** Add golden fixtures for
`EngineService.process_observation` (§4 row 1) — 3+ deterministic observation→InterpretedSignal cases.
This is the regression net; it is achievable today and touches no engine code.

**Phase 2 — Freeze the port contract on paper.** Resolve the `Signal` vs `InterpretedSignal` vs
`EngineResult` ambiguity (§3, §6) in the port definition *before* migrating anything. Pick the scoring
contract. Get sign-off.

**Migration ordering (only if Phase 0 → A and engines are to be exposed for scoring):**
1. **ATR** then **Risk** — already implement `EnginePort` directly, smallest, statistically stable,
   no order-book dependency. Safest first.
2. **Trend → Volatility → Regime** — stable, OHLCV-only, deterministic.
3. **Liquidity → Orderflow** — defer until/unless an order-book feed exists; otherwise they only ever
   hit the no-data branch.
4. **ML Weight — LAST, and behind its own port.** Online learning + feedback method + path-dependence
   make it the highest-risk and the one that breaks the "stateless score" model.

**Engines that MUST NOT be unified early:**
- **ML Weight** (path-dependent, non-deterministic, needs feedback surface).
- **`dynamic_engine_manager` ensemble/selector** (different contract → `FusionPort`, not `EnginePort`).
- **`enhanced_engine_adapters` Microstructure** (contains a guaranteed `NameError`; fix or drop first).
- **The orphan `EngineInterface`/`EngineResult.compute`** (no implementers; either adopt as the
  scoring contract deliberately or delete — don't migrate engines *to* it implicitly).

**Stability safeguards:**
- Keep the live `process_observation` path untouched throughout; consolidation must be additive until
